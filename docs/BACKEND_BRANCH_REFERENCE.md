# FruktAI — backend пополнения склада

Backend MVP для подготовки объяснимых рекомендаций по закупкам у поставщиков. Сервис читает подготовленный CSV-набор, очищает историю спроса для расчёта, оценивает спрос на период поставки, учитывает страховой запас и доступный товар, сохраняет запуск в SQLite и возвращает рекомендации по SKU.

> Документ описывает backend-реализацию из ветки `codex/backend` и его текущие ограничения. Он не утверждает, что каждый упомянутый в разделе метод уже подключён к активному API. Детерминированный Python-расчёт является источником чисел; OpenAI — необязательный слой текстовых пояснений.
>
> Интеграционное примечание: на момент подготовки документа `origin/main` (commit `35ee99e`) содержит frontend и API-контракт, но ещё не содержит backend-код из `codex/backend`. Поэтому команды запуска, API и пути файлов ниже описывают backend-ветку и станут исполняемыми из `main` после отдельного слияния backend-реализации. Этот документ сам по себе backend-код не переносит.

## Возможности и архитектура

Основной поток:

```text
data/<dataset>/*.csv
        │
        ▼
валидация схемы, SKU, чисел и дат
        │
        ▼
детерминированный расчёт спроса и заказа (Python/pandas/NumPy)
        │
        ├── необязательно: OpenAI добавляет только текст в reasons
        │
        ▼
сохранение запуска и рекомендаций в SQLite
        │
        ▼
FastAPI: ответ пересчёта / детализация SKU / сводка / CSV
```

Важные принципы:

- Одинаковые входные данные, дата расчёта и overrides дают одинаковые числовые рекомендации. `run_id` и `generated_at` — идентификаторы/метаданные запуска и поэтому не обязаны повторяться.
- Выбросы отмечаются и исключаются из регулярной оценки спроса, но исходные CSV физически не переписываются.
- В API запрещены отрицательные количества; входные числа, даты и ссылки на SKU проверяются.
- Будущие продажи не участвуют в расчёте: история обрезается до текущей даты системы. Дата расчёта берётся из последней доступной даты истории и ограничивается текущим днём.
- OpenAI не рассчитывает заказ. Его ответ не разбирается как структурированные данные и не может менять количество, срочность, остатки или коэффициенты.

Основные каталоги:

| Путь | Назначение |
| --- | --- |
| `backend/main.py` | FastAPI endpoints, загрузка CSV и формирование контрактных ответов |
| `backend/calculation.py` | Основная детерминированная расчётная логика |
| `backend/services/replenishment.py` | Позиция запасов, округление заказа, reorder point |
| `backend/services/forecasting.py` | Экспериментальные модели и rolling-origin backtest; не подключены к основному API-пути |
| `backend/ai_explainer.py` | Необязательное OpenAI-пояснение с защитой расчётных полей |
| `database/schema.sql` | Таблицы, ограничения, индексы и представления SQLite |
| `database/repository.py` | Инициализация, запись запусков, чтение результатов и экспорт |
| `data/demo/` | Демонстрационный набор из шести CSV |
| `tests/` | Тесты расчёта, API, SQLite и AI-слоя |

## Запуск

Команды ниже выполняются из корня репозитория. В активном виртуальном окружении должны быть установлены используемые проектом пакеты: FastAPI, Pydantic, pandas, NumPy, Uvicorn и pytest.

PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

Либо без активации окружения:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

При старте приложение создаёт SQLite-файл и применяет схему. По умолчанию БД находится в `artifacts/fruktai.sqlite`; каталог `artifacts/` создаётся при первом подключении.

## Переменные окружения и OpenAI

Шаблон безопасных значений находится в `.env.example` backend-ветки. В нём нет настоящего ключа; настоящий `.env` и варианты `.env.*` исключаются из Git корневым `.gitignore` в этой ветке. **Не вставляйте секрет в README, frontend, тесты или Git.**

Приложение читает настройки из переменных окружения процесса. Само по себе оно не загружает `.env`-файл. Для локального PowerShell-сеанса:

```powershell
$env:FRUKTAI_DATA_ROOT = "data"
$env:FRUKTAI_DATABASE_PATH = "artifacts/fruktai.sqlite"
$env:OPENAI_EXPLANATIONS_ENABLED = "true"
$env:OPENAI_API_KEY = "<ваш ключ>"
$env:OPENAI_MODEL = "gpt-6-astra"
$env:OPENAI_TIMEOUT_SECONDS = "20"
$env:OPENAI_MAX_EXPLANATION_ITEMS = "6"
python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

OpenAI-настройки:

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `OPENAI_API_KEY` | пусто | Ключ Responses API; нужен только если AI-пояснения включены |
| `OPENAI_MODEL` | `gpt-6-astra` | Текстовая модель; задайте model ID, доступный вашему API-проекту |
| `OPENAI_EXPLANATIONS_ENABLED` | `false` | Включает необязательное текстовое пояснение |
| `OPENAI_TIMEOUT_SECONDS` | `20` | Таймаут одного запроса |
| `OPENAI_MAX_EXPLANATION_ITEMS` | `20` в коде; `6` в примере | Максимум рекомендаций на один запуск, для которых запрашивается текст |

Если пояснения выключены, ключ не требуется, сетевых запросов к OpenAI нет. Если включены, ключ проверяется при старте приложения. На каждую обрабатываемую позицию делается отдельный запрос; после первой ошибки дальнейшие AI-вызовы этого запуска прекращаются, а обычные рекомендации остаются доступными. AI-текст ограничивается 500 символами и добавляется как `AI-пояснение: ...` в существующий массив `reasons`.

## Формат данных

API принимает имя набора (`dataset`), а не multipart-файлы. Для `dataset=demo` backend читает каталог `data/demo/`. Имена CSV и обязательные колонки:

| Файл | Обязательные колонки | Назначение |
| --- | --- | --- |
| `products.csv` | `sku,name,supplier_id,active` | Товары и признак активности |
| `suppliers.csv` | `supplier_id,supplier_name,lead_time_days` | Поставщики и срок поставки в днях |
| `sales.csv` | `date,sku,units` | Продажи по дате, SKU и единицам |
| `inventory.csv` | `sku,on_hand` | Текущий остаток |
| `in_transit.csv` | `sku,quantity,expected_date` | Ожидаемые поставки |
| `stockouts.csv` | `sku,start_date,end_date` | Интервалы отсутствия товара |

Все шесть файлов должны присутствовать, включая пустые файлы с заголовками, если записей нет. Для используемого набора:

- SKU нормализуется: пробелы по краям удаляются, регистр приводится к верхнему;
- SKU товаров и ID поставщиков должны быть уникальны;
- каждый активный SKU должен иметь остаток и ссылку на существующего поставщика;
- даты должны читаться как даты, количество и lead time должны быть числовыми и неотрицательными;
- ссылки на неизвестные SKU и некорректные интервалы stockout отклоняются;
- поступление учитывается в позиции запасов, если `expected_date` попадает в горизонт `as_of + lead_time_days`.

Демо покрывает стабильный спрос, сезонный профиль, рост, stockout, всплеск закупки и позицию с крупной поставкой в пути. Демо — синтетические проверочные данные, а не фактическая статистика компании.

## API

Интерактивная документация FastAPI после старта: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs).

### `GET /health`

Проверка доступности процесса:

```json
{"status":"ok"}
```

Этот endpoint проверяет приложение, но не является отдельной проверкой готовности SQLite.

### `POST /api/v1/recalculate`

Пример запроса:

```json
{
  "dataset": "demo",
  "overrides": [
    {"sku": "STABLE-001", "on_hand": 25, "in_transit": 10}
  ]
}
```

`dataset` — имя каталога данных из `FRUKTAI_DATA_ROOT`; допускаются латинские буквы, цифры, `_` и `-`. `overrides` необязателен. На SKU можно передать не больше одного override; он должен содержать хотя бы `on_hand` или `in_transit`. Значения — целые числа `>= 0`; overrides действуют только на этот запуск и не меняют CSV.

Ответ соответствует backend response contract:

- `run_id`, UTC `generated_at`;
- `summary`: число SKU, сумма заказа, high-risk SKU, аномалии и SKU с компенсацией stockout;
- `recommendations`: SKU, товар/поставщик, количество, срочность, остатки, срок поставки, спрос, прогноз, safety stock, коэффициенты, покрытие и объяснения;
- `agent_steps`: семь шагов прохождения workflow.

Точные поля ответа:

| Объект | Поля |
| --- | --- |
| `summary` | `total_items`, `total_units_to_order`, `high_risk_items`, `anomalies_removed`, `estimated_stockout_items` |
| recommendation | `sku`, `name`, `supplier_id`, `supplier_name`, `recommended_qty`, `urgency`, `on_hand`, `in_transit`, `lead_time_days`, `avg_daily_demand`, `forecast_demand`, `safety_stock`, `seasonality_factor`, `growth_factor`, `stockout_compensation`, `outlier_units_removed`, `days_of_cover`, `reasons` |
| agent step | `step`, `status`, `message`. Шаги: `load_data`, `validate_data`, `detect_outliers`, `estimate_lost_demand`, `calculate_recommendations`, `validate_result`, `save_result` |

`urgency` принимает `high`, `medium` или `low`. Decimal-значения ограничиваются конечными числами; количества и коэффициенты, определённые контрактом как целые, возвращаются целыми.

`recommended_qty` — целое неотрицательное количество в базовых единицах товара. Пример:

```powershell
$payload = @{ dataset = "demo"; overrides = @() } | ConvertTo-Json -Depth 6
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/recalculate -ContentType "application/json" -Body $payload
```

### `GET /api/v1/items/{sku}`

Возвращает детализацию SKU из последнего сохранённого запуска: `history` (дата, продажи, outlier/stockout flags и оценка упущенных единиц) и `calculation` (поля рекомендации). До первого расчёта неизвестная позиция возвращает `404`.

Каждая запись `history` содержит `date`, `units`, `is_outlier`, `is_stockout` и `estimated_lost_units`. `calculation` повторяет расчётные поля рекомендации и её `reasons`.

### Дополнительные endpoints

В текущем backend также присутствуют:

- `GET /api/v1/summary` — агрегаты последнего запуска;
- `POST /api/v1/orders/approve` — сохраняет подтверждение/отклонение человеком; не отправляет заказ поставщику;
- `GET /api/v1/orders/export.csv` — CSV последней рекомендации по SKU.

Эти endpoints являются дополнительными к основному response contract. Их контракт и ответственность нужно согласовать с владельцами API/frontend, прежде чем на них полагаться в интерфейсе.

Типовые ошибки: `404` для отсутствующего набора или SKU; `422` для некорректных входных данных, overrides или ошибки доступа к БД при пересчёте; непредвиденные ошибки FastAPI возвращает как `500`.

Ошибки приложения возвращаются с полем `detail`; FastAPI validation error сохраняет стандартный массив `detail` с ошибками полей.

## Алгоритм и формулы

Обозначения: `d` — скорректированный средний дневной спрос; `L` — lead time; `R` — review period (в текущем CSV/API не задаётся, поэтому обычно `0`); `S` — коэффициент сезонности; `G` — коэффициент роста; `Z=1.65`; `σ_d` — стандартное отклонение очищенного дневного спроса.

### 1. Регулярный спрос и устойчивые выбросы

Если история содержит не менее четырёх наблюдений, основная проверка использует Modified Z-score:

```text
MAD = median(|xᵢ − median(x)|)
Mᵢ = 0.6745 × (xᵢ − median(x)) / MAD
potential outlier: |Mᵢ| > 3.5
```

Порог `3.5` — правило маркировки потенциального выброса, а не доказательство ошибки исходных данных. Если `MAD=0`, используется IQR-граница `Q3 + 1.5 × IQR`; для плоской серии — ограниченный fallback `3 × max(median, mean, 1)`. При истории короче четырёх наблюдений выбросы не отбрасываются. Количество исключённых единиц возвращается в `outlier_units_removed`; исходный CSV не меняется.

Дополнительная защита пытается выявлять аномально крупный объём на клиента. Однако текущий CSV/API адаптер не принимает `customer_id` и присваивает продажам одинаковое значение `anonymized-unavailable`; поэтому клиентскую часть нельзя считать действующей на этих данных. Для полноценной проверки нужно передавать реальный псевдонимизированный ID клиента и добавить отдельные тесты.

### 2. Упущенный спрос при stockout

В MVP реализована заданная линейная оценка:

```text
lost_demand = normal_daily_demand × stockout_days
```

Дни stockout исключаются из обычных наблюдений; для них в анализ добавляются нулевые записи, если в исходном CSV не было строки на эту дату. Это приближение по среднему спросу. Оно не моделирует изменение спроса внутри каждого дня и не заменяет историю наличия/транзакций.

### 3. Сезонность и рост

Коэффициент сезонности `S`:

- если для товара задан фактор — используется он, ограниченный диапазоном `[0.5, 2.0]`;
- иначе при достаточной истории текущий календарный месяц сравнивается с базовым уровнем спроса;
- при короткой истории или нулевой базе применяется fallback `S=1.0`.

Рост оценивается как отношение среднего недавнего окна к более раннему окну. При истории короче 14 дней `G=1.0`; сырая скорость роста ограничена `[-0.20, +0.50]`:

```text
growth_rate = clip(recent_mean / older_mean − 1, −0.20, +0.50)
growth_factor = 1 + growth_rate
```

Границы не позволяют бесконечно экстраполировать короткий тренд. Текущий MVP использует простую эвристику, а не Holt/Holt–Winters. Для реальной модели коэффициенты следует оценивать только на обучающей части временного ряда и проверять rolling-origin backtest.

### 4. Прогноз на период защиты и страховой запас

Период защиты запасом:

```text
protection_period = lead_time_days + review_period_days
```

Текущий прогноз:

```text
forecast_demand = d × protection_period × S × G + lost_demand
```

Страховой запас для фиксированного lead time и дневной независимой вариации:

```text
safety_stock = max(0, Z × σ_d × sqrt(protection_period))
Z = 1.65
```

Это упрощённая модель: в исходных CSV нет истории фактического lead time, поэтому неопределённость сроков поставки не оценивается. Если появятся данные о распределении срока поставки, можно рассмотреть формулу, учитывающую обе вариации:

```text
SS = Z × sqrt(L × σ_d² + d² × σ_L²)
```

где `σ_L` — стандартное отклонение срока поставки. Формулы safety stock зависят от предположений о независимости и распределении спроса/lead time; выбранное упрощение следует считать MVP-фолбэком, а не универсальной политикой запасов.

### 5. Доступная позиция и заказ

Для основного CSV/API пути:

```text
inventory_position = on_hand + eligible_in_transit
recommended_qty = ceil(max(0, forecast_demand + safety_stock − inventory_position))
```

Поставка учитывается, только если ожидается не позже конца периода поставки. Количество в HTTP-ответе округляется вверх до целого по контракту.

В `backend/services/replenishment.py` есть более общий расчёт, который дополнительно умеет учитывать резервы, backorders, pack size, MOQ и max stock. Текущие обязательные CSV и HTTP override этих параметров не задают, поэтому в основном демо используются `reserved=0`, `backorders=0`, pack size `1`, MOQ `0` и без верхнего лимита.

Срочность: `high`, когда нужно заказать и позиция запасов ниже точки заказа; `medium`, когда заказ нужен, но порог срочности не превышен; `low`, когда заказывать сейчас не нужно. Объяснения в `reasons` показывают числовые факторы; включённый AI может добавить только дополнительный текст.

### Методы из литературы, пока не подключённые к активному API

`backend/services/forecasting.py` содержит эксперименты с сезонным наивным прогнозом, median baseline, Croston SBA и rolling-origin evaluation. Основной `POST /api/v1/recalculate` сейчас использует расчёт из `backend/calculation.py`, а не автоматический выбор Holt–Winters/Croston. Наличие функции в модуле не означает, что она участвует в пользовательском результате.

Если сравнивать будущие модели, используйте временную cross-validation с прогнозным горизонтом, близким к lead time. Для ошибок `eₜ = yₜ − ŷₜ`:

```text
MAE  = mean(|eₜ|)
RMSE = sqrt(mean(eₜ²))
```

MAPE нельзя бездумно применять к нулевым/почти нулевым продажам: метрика неопределена при `yₜ=0` и нестабильна около нуля. Для сравнения разных SKU обычно полезнее дополнить MAE/RMSE масштабированной метрикой, например MASE, и отдельно смотреть смещение прогноза.

## SQLite

Путь задаётся через `FRUKTAI_DATABASE_PATH`, по умолчанию `artifacts/fruktai.sqlite`. SQLite создаётся/инициализируется автоматически. Включены внешние ключи и ожидание блокировки до 5 секунд.

Основные таблицы:

| Таблица | Что хранит |
| --- | --- |
| `suppliers`, `products` | Справочники поставщиков и товаров |
| `sales`, `inventory`, `in_transit`, `stockouts` | Текущий снимок входных фактов |
| `calculation_runs` | Метаданные каждого расчёта и агрегаты |
| `run_overrides` | Остатки/товар в пути, переопределённые для запуска |
| `recommendations` | Рекомендации и сохранённый JSON расчёта |
| `item_history` | Дневная история для детализации SKU |
| `agent_steps` | Состояния этапов workflow |
| `approvals` | Решение человека по последнему заказу |

Представления: `latest_recommendations` и `supplier_order_summary`.

**Текущая граница хранения:** рекомендации и история расчётов привязаны к `run_id`, а таблицы исходных фактов обновляются по SKU при новом запуске. Поэтому это не неизменяемый исторический снимок каждого загруженного датасета; воспроизводимость старых прогонов по исходным фактам пока ограничена. Для нескольких независимых наборов данных нужна версия источника/dataset ID на каждой строке или таблицы фактов с `run_id`.

## Проверки и тесты

Запустить backend-набор из корня проекта:

```powershell
python -m pytest -q tests
```

Ключевые проверки покрывают:

- увеличение `on_hand` или `in_transit` не увеличивает рекомендацию;
- stockout создаёт положительную компенсацию спроса;
- крупная единичная продажа не должна резко менять регулярный прогноз;
- сезонность ограничена допустимым диапазоном;
- заказ неотрицателен;
- API возвращает contract-поля, пересчитывает overrides и сохраняет результат в SQLite;
- AI-слой добавляет пояснение, сохраняет его в истории SKU, но не меняет числовые поля;
- ошибка/некорректный ответ AI оставляет обычное детерминированное объяснение.

Offline AI-прогон (не требует реального ключа и не вызывает OpenAI):


Для проверки реального ключа включите AI и выполните обычный запрос к `/api/v1/recalculate`. Это расходует API budget; автоматический тест никогда не делает настоящий внешний вызов.

## Известные ограничения и следующие шаги

Перед production или реальным пополнением стоит закрыть:

1. Передавать псевдонимизированный `customer_id`, чтобы клиентская проверка крупных покупок работала, либо явно оставить только MAD/IQR по SKU.
2. Сохранять неизменяемые входные снимки с привязкой к `run_id`/dataset и добавлять тест двух разных наборов данных.
3. Передавать из обработки реальный `is_outlier` в `item_history`; сейчас поле истории не отражает весь outlier-анализ, а потерянный спрос распределяется по отмеченным дням равномерно.
4. Исправить/уточнить `anomalies_removed`: контракт определяет это как число наблюдений, а текущий API summary считает SKU с положительным `outlier_units_removed`.
5. Валидировать все значения/даты всех CSV строго, включая неиспользуемые строки, и сообщать предупреждение при устаревшей истории.
6. Пересчитать сезонность и тренд на очищенном скорректированном ряде; добавить сезонную историю за полный сезонный цикл.
7. Использовать rolling-origin backtest без утечки будущего, сравнивать baseline/Holt/Holt–Winters и Croston/SBA по применимым сегментам SKU.
8. Добавить статистику lead time, service level и корректную safety-stock модель под выбранные бизнес-цели.
9. Согласовать API для сгруппированного заказа по поставщику и проверить его с frontend/API contract владельцами.
10. Добавить readiness check БД отдельно от `/health`, миграционные тесты и конкурирующие пересчёты.

Текущие CSV не содержат денег/стоимости хранения, поэтому оптимизация стоимости запасов, бюджета закупки, MOQ и поставщицких ограничений ещё не является частью активного сценария.

## Источники формул и методов

Ссылки ниже — теоретические первоисточники/учебные материалы. Они обосновывают методы и ограничения, но не означают, что каждая формула уже реализована в MVP:

1. **Modified Z-score и порог 3.5** — [NIST/SEMATECH e-Handbook, Detection of Outliers](https://www.itl.nist.gov/div898/handbook/eda/section3/eda35h.htm). NIST приводит `Mᵢ = 0.6745(xᵢ − median(x))/MAD` и предлагает считать `|Mᵢ| > 3.5` потенциальным выбросом для дальнейшей проверки.
2. **Holt linear trend** — [Forecasting: Principles and Practice, Holt’s linear method](https://otexts.com/fpp3/holt.html). Источник формул уровня/тренда и прогноза `ŷ(T+h)=ℓ(T)+h·b(T)`.
3. **Holt–Winters, additive и multiplicative seasonality** — [Forecasting: Principles and Practice, Methods with seasonality](https://otexts.com/fpp3/holt-winters.html). Описывает отдельный сезонный компонент и критерий выбора аддитивного/мультипликативного представления.
4. **Rolling forecasting origin** — [Forecasting: Principles and Practice, Time series cross-validation](https://otexts.com/fpp3/tscv.html). Каждый validation-набор использует только наблюдения, доступные до точки происхождения прогноза; горизонт можно сделать многопериодным.
5. **MAE/RMSE и процентные метрики** — [Forecasting: Principles and Practice, Evaluating point forecast accuracy](https://otexts.com/fpp3/accuracy.html). Разбираются определения MAE/RMSE и то, почему MAPE неопределена при нулевом факте/неустойчива около нуля; также предлагаются scaled errors.
6. **Croston и Syntetos–Boylan Approximation (SBA)** — [Syntetos & Boylan (2005), The accuracy of intermittent demand estimates](https://doi.org/10.1016/j.ijforecast.2004.10.001). Работа сравнивает методы для прерывистого спроса; SBA — модификация оценки Croston с поправкой вида `(1 − α/2) × z′/p′`, уменьшающей его положительное смещение.
7. **Safety stock с вариацией спроса и lead time** — [MIT/King, Determining appropriate inventory levels](https://web.mit.edu/2/2.810/www/files/readings/King_SafetyStock.pdf). Рассматривает safety stock как функцию service Z-score, вариативности спроса, периода защиты и изменчивости lead time, а также различает cycle service level и fill rate.

### Примечание к источникам

Все внешние ссылки проверены при подготовке README. При изменении расчётного алгоритма сначала обновите описание фактической формулы и тесты, затем ссылки/обоснование; не приписывайте MVP сложность Holt–Winters, Croston/SBA или MIT variable-lead-time формулы, пока эти методы реально не подключены и не прошли backtest.
